# apidoc 使用指南

从零开始：装好工具 → 写注释 → 生成文档 → 导入 Apifox 看。

适合第一次用的人。想了解某个细节的完整语义，配合 [README](../README.md) 和 [诊断码说明](diagnostics.md) 一起看。

---

## 一、它解决什么问题

传统做法是「接口写完了，再手工写一份接口文档」，然后代码一改，文档就过期。

apidoc 换了思路：**注释就是文档**。你在控制器方法上按约定写注释，它扫源码生成 OpenAPI 3.0 的 `openapi.json`，再丢给 Apifox / Swagger UI 渲染成页面。

三个特点：

- **只读源码**，不用把你的应用跑起来，不用继承任何基类
- **不依赖框架**，ThinkPHP / Laravel / 原生 PHP 都一样用
- **不写注释也能用**，先出一张「接口地图」，之后再慢慢补注释

## 二、安装与初始化

### 2.1 安装

在项目根目录（`composer.json` 所在处）：

```bash
composer require --dev kontirol/apidoc
```

装在 `require-dev` 里，生产环境不会带上它。要求 PHP 7.4+。

装完会在 `vendor/bin/apidoc` 生成可执行入口。

### 2.2 建一个配置文件

在项目根目录建 `apidoc.php`：

```php
<?php

return [
    // 要扫哪些目录、这些文件属于哪个命名空间
    'controllers' => [
        [
            'path' => __DIR__ . '/app/api/controller',
            'namespace' => 'app\\api\\controller',
        ],
    ],

    // 输出文件
    'output' => [
        'json' => __DIR__ . '/public/openapi.json',
    ],

    'info' => [
        'title' => '预约挂号接口文档',
        'version' => '1.0.0',
    ],

    // 关键：ThinkPHP 8 的控制器文件不带 Controller 后缀
    'scan' => ['suffix' => '.php'],
];
```

三个必须改的地方：

| 配置项 | 说明 |
|---|---|
| `controllers[].path` | 控制器目录的**绝对路径**，用 `__DIR__ . '/相对路径'` 写 |
| `controllers[].namespace` | 该目录对应的命名空间，**反斜杠要写两个**（`app\\api\\controller`） |
| `scan.suffix` | **ThinkPHP 必看**：TP8 默认 `controller_suffix = false`，文件叫 `User.php` 而不是 `UserController.php`，而 apidoc 默认只扫 `*Controller.php`。所以必须改成 `'.php'` |

> 配置文件支持 `apidoc.php` / `apidoc.json` / `apidoc.yaml` / `apidoc.yml` 四种，放在项目根目录会被自动找到。用 `-c` 可以指定别的路径。

### 2.3 第一次运行

```bash
vendor/bin/apidoc generate
```

输出大概长这样：

```
apidoc 0.1.2
8 endpoint(s) documented, 1 ignored, in 10 ms.
Written:
  public/openapi.json  (27.4 KB)
```

**如果报「没有扫到任何接口」**，八成是 `suffix` 或 `path` 配错了。用 `-v` 看细节：

```bash
vendor/bin/apidoc generate -v
```

它会打印扫了哪些目录、跳过了哪些文件、每个文件为什么被跳过。

### 2.4 零注释先跑一次（可选）

老项目第一次接入，方法上都还没写注释，什么也扫不到。这时加 `--all`：

```bash
vendor/bin/apidoc generate --all
```

`--all` 会把**没有 apidoc 标签的方法也全部纳入**：

- URL 按 ThinkPHP pathinfo 约定推（见 [第五节](#五url-是怎么来的)）
- HTTP 方法从方法名猜
- `summary` 用方法名
- 参数从方法签名反射出来

你会得到一张完整的「项目里有哪些接口」的地图，每条都带 `endpoint.undocumented` 提示，标明「这是猜的」。

也可以在配置里常开：`'include_undocumented' => true`。

之后再往注释里补 `@name` / `@param` / `@response`，文档质量自然就上来了。**全部补完后建议改回 `false`** —— 这样没写注释的接口不会出现在文档里，能倒逼团队写注释。

## 三、注释的两种写法

apidoc 认的是**标准 PHPDoc 块**，也就是 `/** ... */`（注意是两个星号开头）。写在方法**正上方**。

```php
    /**
     * @name 用户列表
     * @method GET
     */
    public function index()
    {
```

单行注释 `// 用户列表` 和 `/* 用户列表 */` 都不认。

### ⚠️ 最重要的一个坑：标签「算不算数」

apidoc 判断「这个方法是接口吗」，看的是**有没有下面这 10 个标签之一**：

```
@name   @route  @method  @group  @tag
@param  @response  @body  @bodyParam  @ignore
```

**`@desc`、`@auth`、`@deprecated` 不在这份名单里** —— 它们只是修饰。

所以这种写法**会被整个跳过**：

```php
/**
 * @desc 返回当前用户的就诊人列表     ← 只有 @desc，不算接口
 * @auth bearer
 */
public function getprofile()
```

必须再加一个「算数」的标签才行，通常加 `@name` 或 `@method`：

```php
/**
 * @name 就诊人列表          ← 加了这个，才算接口
 * @desc 返回当前用户的就诊人列表
 * @auth bearer
 */
public function getprofile()
```

**记住一句话：一个方法至少要有 `@name` 或 `@method`，否则 apidoc 当它不存在。**

### 最小可用

只想让接口出现在文档里，写两个标签就够：

```php
/**
 * @name 就诊人列表
 * @method POST
 */
public function getprofile()
```

`@route` 和 `@tag` 能自动推，`@param` / `@response` 不写就是空白（响应会自动补一个 `200 成功`），但至少接口有了、路径对了、方法对了。

### 完整模板

认真写的话，一个接口长这样：

```php
/**
 * @name 添加就诊人
 * @desc 校验短信验证码后新增一个就诊人，一个账号最多 4 个。
 *       验证码 5 分钟内有效，同一手机号 60 秒内只能发一次。
 * @method POST
 * @tag 用户
 * @auth bearer
 * @body {"name":"张三","idcard":"441234199001010000","phone":"13800000000","verifycode":"1234"}
 * @response 200 {"code":200,"message":"操作成功","data":true}
 * @response 400 {"code":400,"message":"验证码错误"}
 */
public function addprofile()
```

下面逐个讲。

## 四、逐个标签详解

### 4.1 `@name` / `@desc`

| 标签 | 说明 |
|---|---|
| `@name` | **接口标题**，显示在列表上（对应 OpenAPI 的 `summary`）。不写的话用方法名 |
| `@desc` | **详细说明**（对应 `description`）。支持多行 |

**`@desc` 多行怎么写？** 续行只要**不以 `@` 开头**就行，缩进、`*` 都对不对齐无所谓（apidoc 会先剥掉每行的 `*` 再判断）：

```php
/**
 * @name 发送短信验证码
 * @desc 给指定手机号发送验证码。
 * 同一手机号 60 秒内只能发一次，每天上限 10 条。
 * @method POST
 */
```

遇到下一行以 `@` 开头，或者遇到空行，说明这段就结束了。

**注意**：只写 `@desc` 不写 `@name` 时，`@desc` 不会变成标题 —— 标题还是方法名。想要好标题就老老实实写 `@name`。

### 4.2 `@method`

HTTP 方法：`GET` / `POST` / `PUT` / `DELETE` / `PATCH` / `HEAD` / `OPTIONS`。

**不写 apidoc 会从方法名猜**，猜的规则在 [4.11](#411-http-方法是怎么猜的) 讲。**名字看不出来的就明确写出来** —— 比如 `checkCode`、`myorders`、`orderDetail` 这类，猜不出来会掉到 `GET`，而它们实际可能是 POST。

### 4.3 `@route`

请求路径，`{name}` 表示路径变量：

```php
/**
 * @route /api/user/detail/{id}
 * @method GET
 * @param int! id 用户 ID
 */
```

`{id}` 会**自动变成 OpenAPI 的 path 参数**，并且强制 `required: true`，不用再写 `@param` 声明它 —— 写了 `@param int! id 用户 ID` 的话，会把类型和说明用上，比自动生成的好。

**不写 `@route` 也不会瞎编** —— 见 [第五节](#五url-是怎么来的)。

### 4.4 `@tag`（别名 `@group`）

给接口分组，Apifox / Swagger UI 里会按这个把接口折叠成一块。

```php
@tag 用户           // 单个
@tag 用户
@tag 挂号           // 写多个，接口会同时出现在两组里
```

**不写 `@tag` 就没有分组** —— 该接口会归到「未分组 / default」那一类。apidoc **不会**按 URL 前缀自动分组建 tag，所以想让文档有条理，`@tag` 得自己写。

想在文档里给分组写说明，配置里加 `tags`：

```php
'tags' => [
    '用户' => '用户中心的接口，包含登录、就诊人管理',
    '挂号' => '号源查询、锁号、下单、支付',
],
```

### 4.5 `@auth`

标记鉴权方式：

| 写法 | 含义 | 渲染效果 |
|---|---|---|
| `@auth none` | 不需要登录 | 公开接口，不带锁图标 |
| `@auth bearer` | 需要 `Authorization: Bearer xxx` | 带锁，Apifox 里可填全局 token |
| `@auth apikey` | 需要 API Key（Header 或 query） | 带锁 |

**不写就是不标**（既不是 none 也不是 bearer）—— 建议明确写清楚，特别是公开接口，否则前端会以为是忘了标。

`bearer` / `apikey` 对应配置里的 `security.schemes`，见 [README 的配置项章节](../README.md#配置项)。

### 4.6 `@param`

写请求参数。语法：

```
@param <类型> <名字>[=<默认值>] <说明>
```

**类型后面加 `!` 表示必填**：

```php
@param int page=1 页码          // 可选，默认 1
@param int! id 用户 ID          // 必填
@param string keyword 关键字     // 可选，无默认值
```

名字前面带不带 `$` 都行（`@param int $page` 和 `@param int page` 一样）。

类型映射表：

| 你写的 | 生成 OpenAPI 的 |
|---|---|
| `int` / `integer` | `integer` |
| `float` / `double` / `number` / `decimal` | `number` |
| `bool` / `boolean` | `boolean` |
| `array` / `list` / `object[]`；任意类型加 `[]` | `array` |
| `object` / `json` / `map` | `object` |
| 其它（含 `string`） | `string` |

**联合类型取第一个非 `null` 的**：`@param int|null id` → `integer`。
**`?` 会被去掉**：`@param ?int id` → `integer`。

**默认值会按类型转换**：`@param int page=1` → 数字 `1`；`@param bool flag=true` → 布尔 `true`。

**一条 `@param` 只能写一个参数**，多个参数就写多行：

```php
/**
 * @param int page=1 页码
 * @param int size=10 每页数量
 * @param string keyword 昵称关键字
 * @param int! status 状态：0 待付款 1 已付款
 */
```

> **`@param` 描述里的空格没问题**，apidoc 只取前两段当类型和名字，剩下全部拼成说明。

### 4.7 `@body` —— 请求体

四种类型：

```php
@body {"name":"张三","age":18}      // 1. JSON 请求体，自动推断 schema
@body form                          // 2. 表单
@body form name=张三 age=18          // 3. 表单 + 示例值
@body multipart                     // 4. 文件上传，字段用 @bodyParam 声明
@body text                          // 5. 纯文本 body
```

**JSON 那一种最常用**。给一个完整的示例值，apidoc 会自动**反推成 JSON Schema**，所以 Swagger UI / Apifox 里能看到完整的字段树（每个字段名、类型、必填与否）。

**写了 `@body` 就默认是必填请求体**（`required: true`）。

### 4.8 `@bodyParam` —— multipart / 表单的字段

文件上传接口用：

```php
/**
 * @name 上传处方图片
 * @method POST
 * @auth bearer
 * @body multipart
 * @bodyParam file image 处方图片，支持 jpg / png
 * @bodyParam string! order_no 订单号
 * @response 200 {"code":200,"message":"操作成功","data":{"url":"/uploads/2026/10/a.jpg"}}
 */
public function upload()
```

`@bodyParam` 的语法和 `@param` **完全一样**：`@bodyParam <类型> <名字> <说明>`，类型加 `!` 表示必填。

就算不写 `@body`，只写 `@bodyParam` 也会生成请求体（类型默认 json）。

### 4.9 `@response`

```
@response [状态码] {JSON 示例}
```

**不写状态码就是 200**：

```php
@response {"code":200,"message":"操作成功","data":true}
```

**写了状态码就按状态码归**：

```php
@response 200 {"code":200,"message":"操作成功","data":{"token":"a1b2c3"}}
@response 400 {"code":400,"message":"验证码错误"}
@response 401 {"code":401,"message":"未登录或登录已过期"}
```

状态码的中文描述是**自动补的**（200 → 成功，400 → 参数错误……），不用自己写。

**同一个状态码写了两次，后者覆盖前者**，并在 `-v` 下给一条 `response.duplicate` 提示。

**一个 `@response` 都不写会怎样？** apidoc 会自动补一个 `200 成功` 的空响应，所以文档不会出现「没有响应」的接口。

**JSON 里的结构会自动反推成 schema**，包括嵌套对象和数组。所以 `@response` 里给一个结构完整的例子，文档里就能看到字段说明。

### 4.10 `@deprecated` / `@ignore`

```php
@deprecated          // 标记为废弃，文档里会划掉，但还在
@ignore              // 完全排除，不出现在文档里
```

`@ignore` 适合写内部方法、调试接口、临时接口。

> 注意 `@deprecated` **不在这份「算数」名单里**，所以它得跟 `@name` 之类的标签一起用。

### 4.11 HTTP 方法是怎么猜的

没写 `@method` 时，apidoc 从方法名猜，**只认完整的单词**（`save_word` 认，`userinfo` 不认）：

| 猜出的方法 | 触发单词 |
|---|---|
| `DELETE` | delete, destroy, remove, clear, cancel, drop, revoke |
| `PUT` | update, edit, modify, put, patch |
| `POST` | create, store, save, add, insert, submit, send, post, report, upload, login, logout, refresh, register, bind, unbind, publish, approve, reject, pay, payment, start, stop, lock, unlock, close, notify, callback |
| `GET` | 上面都没命中 |

**驼峰会先拆成下划线再匹配**：`sendCode` → `send_code` → 命中 `send` → `POST`。

**判定顺序是 DELETE → PUT → POST → GET**，所以 `deleteOrder` 是 DELETE 而不是 POST。

猜出来的值一定伴随一条 `method.guessed` 提示（`-v` 可见），不会悄悄写错。**名字看不出来的（`checkCode`、`myorders`、`orderDetail`）一定要手写 `@method`。**

## 五、URL 是怎么来的

三条路，优先级从高到低：

### 1. `@route`（最可靠）

写了什么就是什么。**推荐**。

### 2. 按 ThinkPHP 约定推导

不写 `@route` 时，apidoc 会看命名空间和类名：

```
app/api/controller/OrderController.php::myorders()

    命名空间 app\api\controller   →  /api
    类名     OrderController      →  ordercontroller
    方法     myorders             →  myorders
                    ↓
            /api/ordercontroller/myorders
```

规则：

- `app\{应用}\controller` → `/{应用}`（多应用模式）
- `app\controller` → 空的（单应用模式）
- **命名空间不符合这两个约定就完全不推导**，不会给别的框架瞎编 URL

类名和方法的拼法取决于应用配置，apidoc 会自己去读这两个开关：

| 配置项 | 出厂值 | 对 URL 的影响 |
|---|---|---|
| `route.controller_suffix` | `false` | 为 `false` 时**不剥**后缀，`OrderController` → `ordercontroller`；为 `true` 时才剥，`OrderController` → `order` |
| `app.url_convert` | `true` | URL 转小写。ThinkPHP **不做驼峰转下划线**，所以 `orderDetail()` → `orderdetail`，不是 `order_detail` |

> **这两条是最容易搞错的地方。** 很多人生成完发现文档里是 `/api/order/myorders`，而实际地址是 `/api/ordercontroller/myorders` —— 就是默认把 `Controller` 当成要剥掉的后缀了。0.1.2 起已经按应用的真实配置走，不用再手动处理。

**项目本身不走 ThinkPHP 约定时**（自己写了路由、URL 用 kebab-case），手动指定：

```php
'url' => [
    'controller_suffix' => true,   // auto（默认，问框架）| true | false
    'case' => 'kebab',             // auto（默认）| lower | snake | kebab | keep
],
```

推导出来的值会带一条 `route.inferred` 提示，**消息里直接写明推成了什么**，方便你核对：

```bash
vendor/bin/apidoc generate -v | grep route.inferred
```

```
OrderController::myorders() has no @route, /api/ordercontroller/myorders was derived from its namespace.
```

### 3. 读框架路由表（ThinkPHP）

如果你的项目是**注册式路由**（写了 `Route::get('user/detail', 'User/detail')`），可以配：

```php
'route' => ['source' => 'thinkphp'],
```

apidoc 会引导你的应用、读出真实路由表：

- 和 `@route` 冲突时，**以真实路由表为准**，同时给一条 warning
- `@route` 没写但路由表里有，**自动填上**

> **pathinfo 自动路由的项目**（不写 `route/*.php`）也可以开这个 —— ThinkPHP 只注册了一条内置的 `/<MISS>` 兜底路由，apidoc 会把它过滤掉，不会覆盖你的 `@route`。而且同一趟引导会顺带把上面那两个 URL 约定读出来，所以**开了更准**（特别是 `controller_suffix` 被人改过的时候）。

不想要自动推导就加 `--no-infer`，或配置 `'route' => ['infer' => false]`。

## 六、生成与查看

### 生成

```bash
vendor/bin/apidoc generate
```

产物按配置里的 `output` 走。可以同时输出 json 和 yaml：

```php
'output' => [
    'json' => 'public/openapi.json',
    'yaml' => 'public/openapi.yaml',
],
```

### 查看

**方式一：Apifox（推荐，本地客户端）**

```
Apifox → 项目设置 → 导入数据 → OpenAPI/Swagger → 选 public/openapi.json
```

记得选「OpenAPI 3.0」，别选「Swagger 2.0」，那是两个不同格式。

**方式二：在线 Swagger Editor**

打开 [editor.swagger.io](https://editor.swagger.io) → `File → Import File` → 选 json。左边结构、右边渲染，不用装软件。

**方式三：本地网页**

在 `public/apidoc.html` 放一个 Swagger UI 页面，`php think run` 起来后访问 `http://127.0.0.1:8000/apidoc.html`。注意**必须通过 http 打开**，双击 html 文件不行（`file://` 协议下 fetch 本地 json 会被浏览器拦掉）。

**方式四：Postman**

`Import` 拖进 json，每个接口会变成 Collection 里的一条，可以直接发请求。

## 七、命令行速查

```
apidoc generate [选项]     扫描并写出文档
apidoc validate [选项]     只检查，不写任何文件
apidoc version             打印版本
apidoc help                帮助
```

| 选项 | 说明 |
|---|---|
| `-c`, `--config <文件>` | 指定配置文件 |
| `--all` | 连没有 apidoc 标签的方法也一并文档化 |
| `--no-infer` | 不自动推导缺失的 `@route` |
| `--no-reflection` | 不用 PHP 反射补参数 |
| `--strict` | 把 warning 也当成错误 |
| `--no-fail-on-empty` | 一个接口都没扫到时也不报错 |
| `-v`, `--verbose` | 打印扫描的目录和 notice 级诊断 |
| `-q`, `--quiet` | 只打印错误 |
| `-h`, `--help` | 帮助 |

**退出码**（方便挂 CI）：

| 码 | 含义 |
|---|---|
| `0` | 成功 |
| `1` | 跑不起来（配置错、文件不可写……） |
| `2` | 文档生成了，但有 error 级问题（比如两个接口占用同一个「方法 + 路径」） |

`validate` 会额外检查重复路由、缺失路由、缺失标题，适合放进 pre-commit：

```bash
# .git/hooks/pre-commit
#!/bin/sh
vendor/bin/apidoc validate --strict || exit 1
```

## 八、常见问题

### Q1：跑了 generate，说「没有扫到任何接口」

按顺序排查：

1. **`scan.suffix`** —— ThinkPHP 8 的控制器文件是 `User.php` 不是 `UserController.php`，默认后缀扫不到。改成 `'.php'`。
2. **`controllers[].path`** —— 必须是**绝对路径**。用 `__DIR__ . '/app/api/controller'` 这种写法，不要写相对路径。
3. **命名空间** —— `namespace` 要和文件里的 `namespace xxx;` 完全一致，反斜杠写两个。
4. 加 `-v` 看它到底扫了哪些目录、跳过了哪些文件。

### Q2：明明写了注释，接口还是没出现

**看是不是只写了 `@desc` / `@auth` / `@deprecated`** —— 这三个不算数（见 [第三节](#三注释的两种写法)）。加个 `@name` 或 `@method` 就有了。

### Q3：扫到了接口，但 URL 是错的 / 多了一截

先看诊断里有没有 `route.inferred` —— 有就说明这个 URL 是**猜的**，不是从 `@route` 来的。

**对照这两条检查推出来的值：**

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 文档里是 `/api/order/myorders`，实际是 `/api/ordercontroller/myorders` | 类名的 `Controller` 被当成后缀剥掉了，而你的应用是 `controller_suffix = false`（TP 出厂值） | 0.1.2 起会自动读应用配置，不用管；老版本升级，或项目不用 ThinkPHP 约定时，配 `'url' => ['controller_suffix' => false]` |
| 文档里是 `/api/order/order_detail`，实际是 `/api/order/orderdetail` | 驼峰被转成了下划线，ThinkPHP 不做这个转换 | 配 `'url' => ['case' => 'lower']` |
| 整个前缀都不对（比如多了一层 `api`） | 命名空间不是多应用写法，或 `controllers[].prefix` 配错了 | 检查 `prefix` 和命名空间 |

想让它永远准，就手写 `@route`。

### Q4：接口重复了，报 `endpoint.duplicate_route`

同一个「HTTP 方法 + 路径」出现了两次。常见原因：

- 两个控制器方法推出来的 URL 撞了（比如 `User::info()` 和 `Userinfo::index()`）
- `@route` 写重了
- **HTTP 方法猜得不对**：本来是不同的接口，一个猜成 GET 一个猜成 POST 就没事，但如果两个都掉到 GET 又碰巧路径相同就撞了

加 `-v` 会告诉你具体是哪两个。

### Q5：`--all` 出来的方法名当标题，太丑了

那就补 `@name`：

```php
/**
 * @name 就诊人列表
 * @method POST
 */
```

不用一次补完，补一个少一个丑的。

### Q6：我想给接口加参数，但参数是从 `Request::post()` 拿的，方法签名里没有

这正是 apidoc **不用签名做校验**的原因 —— ThinkPHP 里大量参数在方法签名里根本不出现。

用 `@param` 手写就行：

```php
/**
 * @method POST
 * @param int! id 订单 ID
 * @param string type 类型
 */
public function orderDetail()
{
    $id   = Request::post('id');
    $type = Request::post('type') ?? 0;
```

方法签名里有标量参数的话（`detail(int $id)`），apidoc 会**自动补进文档**，不用重复写。

### Q7：怎么让某个方法不出现在文档里？

```php
/**
 * @ignore
 */
public function debugSomething()
```

或者**干脆不写 PHPDoc 块**（前提是没开 `include_undocumented`），它自然就跳过了。

### Q8：生成的 json 里中文是 `\u4e2d\u6587` 这种转义

这是 JSON 的正常编码方式，**不影响导入**。Apifox / Swagger UI / Postman 解析后都会正常显示中文。

如果某个工具显示成了 `????`，那是工具自身编码问题，不是 apidoc 的问题，告诉我具体是哪个工具。

### Q9：`validate` 报了一堆提示，要紧吗？

看诊断码的含义 —— 完整的诊断码和修法在 [diagnostics.md](diagnostics.md)。

几个常见的：

| 诊断码 | 含义 | 要不要修 |
|---|---|---|
| `route.inferred` | URL 是推的 | 想精确就写 `@route` |
| `endpoint.undocumented` | 没有 apidoc 标签（`--all` 收进来的） | 补注释 |
| `endpoint.no_summary` | 没有 `@name` | 补注释 |
| `method.guessed` | HTTP 方法是猜的 | 明确写 `@method` |
| `endpoint.duplicate_route` | 路由重复 | **必须修** |
| `endpoint.no_route` | 找不到 URL | **必须修** |

 * @response  400 {"code":400,"message":"参数错误"}
 * @deprecated
 * @ignore
 */
